### 5.2 根因树

```
E2-A 第 1 项“连续出现缺口与证据不一致”
├─ RC1 没有“规则 → 约束”的显式规格层（语义模型缺位）          → P1、P2、P5、（P7）
│     校验按“查表时用到哪些键”自下而上写，没有一份可对照的约束清单；
│     测试与代码同一作者同时写，只能确认“代码做了它做的事”。
│     输入约束（IN-*）也从未列为规格，所以只测了正常路径。
├─ RC2 验证架构未分层，独立正确性基准不可执行                    → P2、P4、P7
│     三方比对（G-1）只是一份离线报告，没有进入任何 CI，也没和现行 CSV 哈希绑定；
│     引擎向量只抽样。验收方只能要求 L2 运行时校验去承担 L3 数值正确性，于是逐条补。
├─ RC3 证据靠人工转录，脚本放在仓库外                            → P3
│     变异脚本、快照脚本临时写在仓库外，报告数字手抄；
│     CI 里没有任何一步产出这些证据，无法复现，口径漂移。
└─ RC4 “契约未写”的实现选择与准入附带要求没有登记机制           → P6、P8
      CLAUDE.md 第 4 条只靠自觉；
      MANIFEST 只记裁决号，不记规则编号、来源、附带标记。
```

### 5.3 逐问回答

1. **哪些现象同根**：
   - P1、P2、P5 同根于 RC1；
   - P2、P4、P7 同根于 RC2（P2 两根交叉：起首与起点是数值正确性，缺 L3 时才不得不进 L2）；
   - P3 单独源于 RC3；
   - P6、P8 源于 RC4。
2. **为什么原机制没提前发现**：
   - 没有清单可对照（RC1），也没有逐格的独立比对在跑（RC2）；
   - CI 全绿只说明“已写的测试都过”，不说明“该写的都写了”。
3. **会影响其他静态表的根因**：
   - RC1、RC2 会影响以后每一张静态表（月破六冲、飞伏、人元司令天数表、黄历表等），同样会重演；
   - RC3 影响所有阶段的验收证据。
4. **影响后续模块的问题**：
   - RC4 影响 E2 数据库：Term 别名表、补强标记要入库，必须先有登记；
   - IN-BZ 问题影响界面接入：界面会把 E1 的柱结果传给 baziDetail。
5. **一次修复能消除一组问题的**：
   - 修 RC2（可执行的 L3 全覆盖基准）：一次覆盖全部 1,013 格 + 两种计算的全组合，以后任何格子错都会被抓到；同时把“起首、起点”这类问题的证明从靠 L2 补洞，变成 L3 的逐格证明。
   - 修 RC1（约束清单 + 编号进代码和测试 + 自动核对三者一致）：使“漏写校验”在 CI 中可被机器发现。
6. **不属于 E2-A 第 1 项的**：
   - 十神别名表（Term 层，须查证与裁决）；
   - 月建、月破、飞伏（P-B-07、09，E2-A 授权未含）；
   - 人元司令（暂缓）；
   - 界面是否显示补强标记、整理层标注（UI-2）；
   - 藏干次序的独立来源（须研究，见第七节）。
